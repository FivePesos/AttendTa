## Intent

**Problem:** The app has no repeatable way to serve HTTPS on the hotspot LAN, and phones cannot use the camera scanner without a secure context and a trusted certificate. The 8.14 checklist still leaves the host/address/certificate decision BLOCKED, so real phone scanning is unproven.

**Approach:** Add a config-driven Kestrel hotspot mode that binds HTTP on loopback and HTTPS on the hotspot IP, using a local root CA and server certificate generated by a repo CLI. Document phone trust, record the Q2 mechanism decision, verify scan and manual lookup on a real phone, and leave evidence rows BLOCKED when human inputs are absent.

## Boundaries & Constraints

**Always:** Stay offline-capable with a local CA. Match the certificate SAN to the URL host or IP. Keep private keys and passwords out of git, logs and output. Keep the HTTP loopback binding for the readiness check. Leave the scanner UI, engine and policy unchanged. Record evidence with date, host and revision. File scanner defects back to 4.4/4.5.

**Never:** Add IIS, a reverse proxy, a cloud service or a background job. Bind hotspot HTTPS to a wildcard or loopback address. Commit a PFX, password or private key. Disable certificate validation globally. Claim phone or offline PASS without a real run. Rewrite 8.14 history.

## I/O & Edge-Case Matrix

| Scenario | Input / State | Expected Output / Behavior | Error Handling |
|---|---|---|---|
| Hotspot off | `Enabled=false` | Existing HTTP localhost startup; no certificate | No error |
| Valid hotspot | PFX SAN matches the public host; free ports | HTTP loopback plus HTTPS on the LAN IP; readiness login still 200 | No error |

**Acceptance Criteria:**
- Given hotspot mode is off, when the app starts, then it behaves as today and needs no certificate.
- Given a valid PFX and matching public host, when hotspot mode is on, then Kestrel listens on HTTP loopback and HTTPS on the LAN IP/port, and the readiness login still returns HTTP 200.
- Given a missing, wrong-password, expired or SAN-mismatched certificate, when the app starts, then it refuses to listen with a clear message and never prints the password.
- Given a generated certificate, when inspected, then it has the requested SANs, a server-auth EKU, a private key and a chain to the root CA.
- Given a phone with the root CA installed and the hotspot URL open, then Chrome shows no warning and scan/manual lookup work; this is the human step and is PASS only with real evidence.
- Given no real phone or host, when the checklist is produced, then every unverified row is BLOCKED with the missing input named.

## Implementation Notes

- Direct Kestrel listeners replace the default URL binding: a live run bound `127.0.0.1:5080` (HTTP)
  and `192.168.56.1:5443` (HTTPS), left port 5000 unbound, and returned HTTP 200 on the loopback
  login page with no redirect.
- The server PFX must be loaded with a persisted key set (`X509KeyStorageFlags.Exportable`).
  `EphemeralKeySet` produced a certificate SChannel could not use: the TLS handshake closed with
  `UNEXPECTED_EOF` before any request.
- The server certificate includes an Authority Key Identifier (`2.5.29.35`). Without it, strict
  OpenSSL clients reject the chain with `Missing Authority Key Identifier` even when the root is
  trusted.
- The server PFX embeds the public root certificate; the root PFX stays host-only. The command
  refuses to overwrite an existing output directory so a root private key is not lost.
- `dotnet test` reports "Zero tests ran" for both test projects in this SDK/runtime combination
  (pre-existing on the baseline). The tests were verified through the xUnit console runner:
  `dotnet run --project tests/ASI.Basecode.IntegrationTests/... -- -class "*Hotspot*"` ran 35 tests
  with 0 failures, and the Services suite ran 310 with 0 failures.
- 2026-11-08 orchestrator verification: in this environment `dotnet test` did discover the tests.
  `--filter "FullyQualifiedName~Hotspot"` ran 36 tests with 0 failures (the added listener test
  covers the valid-hotspot binding row), and the Services suite ran 310 with 0 failures. The
  earlier "Zero tests ran" note was environment-specific and is superseded.

## Design Notes

A local root CA is the only offline option that gives phones a chain they trust without a public domain or internet. The root private key stays on the host; only the public root certificate goes to phones. The server PFX password is a runtime secret.

Direct Kestrel is required by AD-16. HTTP stays on loopback so the readiness check keeps its HTTP 200 contract; redirecting loopback would present a certificate that may not name `127.0.0.1`. LAN clients use HTTPS directly. Use the hotspot IP in the URL because HSTS does not apply to IP addresses and hotspot DNS is unreliable; the SAN includes that IP. A wildcard bind is rejected so the app is not exposed elsewhere. If the address changes, reissue the server certificate.
