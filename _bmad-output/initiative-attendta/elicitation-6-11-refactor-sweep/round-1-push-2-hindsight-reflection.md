# Round 1 — Push 2 — Hindsight Reflection

Method: Hindsight Reflection — Look back from after it worked.
Form: Written from a year after success: what mattered, what did not, and what the draft spent effort on that never counted.

## Form — Certificate backend sweep (ticket 6.11), written a year after it shipped

A year out, the sweep did what it was meant to do: the tracer is gone, the seven template facts still guard the renderer, and nobody has missed `Empty()` or `ViewerUrl`. What mattered was almost never what the plan spent its words on.

**What mattered.** The one decision that carried the ticket was making the test split the risky part and saying so in Design Notes. That sentence is why the rename kept the five Poppler-reading facts intact and why nobody "cleaned up" the `ci.yml` Poppler step on the way past. The second thing that mattered was the Code Map's line-level honesty: `:354-361` is the signatory section and must become unconditional, `CertificateViewerViewModel.Empty` is used at `CertificateLedgerController.cs:121` — keep, `Startup.DI.cs:59` is the only registration. Those three annotations are what stopped the implementing agent from deleting the wrong `Empty()` and from leaving a dangling DI line. The third was the rejected-findings ledger. It is the only part of the document anyone reread six months later, because it is the only part that records *why not*, and the next sweep reused four of its arguments verbatim.

**What did not matter.** The I/O & Edge-Case Matrix. Two of its four rows restate acceptance criteria the tasks already carry ("no route exists; 404", "unchanged 200 `application/pdf`"), one describes a compile failure, and the fourth says "unchanged" three times. It read as diligence and cost a reviewer a minute. The `risk: medium` and `route: full` front matter never influenced a decision. The Findings Ledger's "Accepted:" line duplicates the task list one-to-one — the same six items, in the same order, with fewer words.

**What the draft spent effort on that never counted.** Line numbers. Roughly half the Code Map's specificity is `:59`, `:115-116,170-172`, `:283-297,299-313,319-322,350-361`, `:569-570,580-581,589-590`. The implementing agent opened the files anyway, because a deletion task at line 350 of a 400-line Razor view is not a place to trust a stale offset, and by execution time the offsets had drifted. The anchors that survived contact were the *symbol names* and the one semantic instruction attached to them. The effort that counted was the sentence after the numbers, not the numbers.

**What we would have done differently, knowing how it went.** We would have named the register-commit check as the one acceptance criterion a reviewer cannot run from the working tree, and said so. And we would have noticed that the plan's own Verification section, as written, cannot be executed on the machine it targets — which is the kind of thing nobody finds until the reviewer tries it.

## Findings

1. **Verification, line 98 — the class-filter command is wrong for xUnit v3.** `dotnet run ... --no-build -- -class <FQN>` is not a supported switch; the v3 runner takes `-class` only inside `-filter` (or `--filter`), e.g. `-filter "FullyQualifiedName~CertificatePdfRendererTests"`. As written the reviewer's "focused affected issuance/download check" fails at argument parsing, not at a test, and the plan's acceptance looks unverifiable. Change both line 98 and line 99 to a single `-filter`-based invocation, and drop `-parallelMode none` unless it is load-bearing (it isn't for a single class).

2. **Verification, line 98 — `--no-build` after a rename that changes the assembly.** The command runs with `--no-build` immediately after `dotnet build` at line 97, but line 97 is `dotnet build` at the solution root, which does not guarantee the integration test project was rebuilt, and the rename (`CertificateTracerFlowTests` → `CertificatePdfRendererTests`) changes the type name the filter matches. State the build target explicitly (`dotnet build tests/ASI.Basecode.IntegrationTests/ASI.Basecode.IntegrationTests.csproj`) or drop `--no-build`.

3. **Verification, lines 97-101 — the "focused affected issuance/download check" never touches the download path.** Acceptance criterion 3 (line 73: "the bytes equal the retained file and the non-owner/unknown refusals are unchanged") is checked only by `CertificateLedgerFlowTests` appearing in a list at line 99 with "expected: all pass" — no named fact, no statement that the download facts live there. A reviewer checking the ticket's verify line cannot tell which test proves criterion 3. Name the specific download/refusal facts (or the class and fact names) and say explicitly that criterion 3 is discharged by them, not by the renderer class.

4. **Tasks, line 67 — the register-commit task asserts values that the plan never shows are verified.** "set M-10a to `46a2100`, M-10b to `d6de0d5`, M-12 to `7637096`" is presented as a transcription, but the Problem statement (line 22) says the current commits "do not exist". Nothing in the plan records how these three SHAs were established, and acceptance criterion 5 (line 75) is the only place ancestry is checked — after the edit. Add the pre-check to the task: state that each SHA was confirmed an ancestor of `dev` at `baseline_revision`, and give the one command the reviewer runs (`git merge-base --is-ancestor <sha> dev`) rather than leaving criterion 5 to prose.

5. **Tasks, line 67 — "correct the summary sentence that says `DemoSeedService` holds no certificate state" is unscoped.** Unlike every other task, this one names no file line and no replacement text; the Code Map entry (line 55) points only at `:94,95,98`, the commit cells. An implementing agent cannot execute this without re-deriving what the sentence should now say, and it sits in tension with the Never clause (line 30) that keeps the demo seam out of scope. Either give the sentence and its corrected form, or drop it from 6.11 and leave it to 8.13.

6. **Code Map, line 48 — the Razor line ranges and the "unconditional" instruction are under-specified for the highest-risk edit.** "the `else` branch at `:354-361` is the signatory section and must become unconditional" tells the agent what to do but not what to delete: the `if` that guards it is presumably the `IsDevelopmentSample` check, and the plan never says so, nor whether the watermark/banner markup at `:283-297,299-313,319-322` shares an enclosing block with it. This is the one edit where a wrong deletion silently changes the official PDF — the exact thing the seven facts exist to catch — yet it gets less precision than the DI registration. State the guard being removed by name and note that the seven facts are the check on this edit specifically.
